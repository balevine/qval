# AGENTS.md

Guidance for agentic coding tools working in this repo: where things live, the invariants to preserve, and the conventions to write to. It describes **how to work here**, not what the product is.

**[`README.md`](README.md) is the authoritative definition of the application.** It says what Qval does, the ticket format, what each command is for, and how the pieces fit. Read it first, and **keep it in sync whenever behavior changes**. A change that makes the README wrong is not finished. Where this file and the README overlap, the README is the one that has to be right, and the orientation below is a summary of it for working purposes.

`.plans/` is gitignored, and it is **where scratch and working documents go**. A review, a worklist, a set of notes to work through. Write them there rather than inventing another directory for them.

The files already in there (`PROJECT_SPEC.md`, `REVIEW.md`, `SKILLIFY.md`) are historical artifacts and are unmaintained, so don't try to keep them current. **Nothing in the code or the docs cites `.plans/`**, and nothing should start. A comment that needs to justify a decision should state the reason itself rather than point at a document the reader may not have.

## What this is

A local-first tool for **evaluating** customer support tickets, shipped as a **Claude Code plugin**. It scores any ticket set in the documented format, a real helpdesk export as readily as a set generated by **Qbort**, its sibling tool. Qbort is one producer of the format, not a dependency, and docs must not imply otherwise. The user imports a ticket set, writes free-text **rules** (how to score), defines a typed **schema** of output properties, runs an **LLM evaluation**, optionally does a **human evaluation** by hand, and saves both into a single `*.qval.json` file. Multiple users' eval files of the same dataset can be **merged** for per-ticket **means/standard deviations** (LLMs and humans disagree even on the same model/criteria).

**Every evaluation has exactly one scorer, named in its config.** `claude` (the default) is the ambient model inside Claude Code, through subagents. `jev` is Typesafe's Jev classifier, which the engine calls itself from Node with no subagents. The scorer is chosen once, by `/qval:draft`, and both run from `/qval:evaluate-tickets`. There is no provider picker and no in-app run. The old provider stack (Ollama, bring-your-own-key, `safeStorage`, the cost estimate) was deleted, not deprecated, and Jev is not a return of it. The parts a person has to do by hand (schema, rules, human eval, comparison) open in a browser tab served by the review server (`/qval:review`). Everything runs locally. Network egress is Claude Code's own, plus `api.typesafe.ai` during a Jev run, and nothing else.

**The Typesafe key lives in `TYPESAFE_API_KEY` and nowhere else.** `plugin/lib/typesafe.mjs` reads it in the engine process and puts it only in the `Authorization` header. It is never a flag, a settings field, a server endpoint, or part of an eval file, so it never crosses to the browser. Every error message passes through `redactKey` before it is printed or stored, so it is never printed. `SKILL.md` tells Claude never to ask for it, echo it, or write it, so it never enters Claude's context. Keep all four true. A new place the key can be supplied, or can appear, is a leak and not a convenience.

Both halves read and write the same `EVAL_SCHEMA.json` and `EVAL_RULES.md` in the working directory, and **only `/qval:draft` creates them** (short of the user writing them by hand). The workflow is `/qval:draft` first, then `/qval:review` and `/qval:evaluate-tickets` in either order. Neither of those two scaffolds a config. `qval serve` refuses a new evaluation without a usable pair (`NO_CONFIG`, exit 2). Half a pair counts as none, and so does a schema with any row that does not survive normalization, because `normalizeSchema` would otherwise quietly fall back to the starter schema. The evaluation skill stops and points at `/qval:draft`. A new session starts from the pair (scorer included), and `serve` writes back what the person actually used, which is what stops the two commands from scoring against different criteria and producing files that will not merge. The write-back is **conditional**: the config fingerprint is taken at session start and again at the end, and the files are only rewritten when it changed. They are the user's files, often hand-written, and a session opened on an older, scored eval file loads *that* file's config. An unconditional write would stamp an archived schema over the current one just for looking at an old result.

A third file, `RULES.md`, is optional and is **never written by anything here**. It is the user's plain-language rules, and `/qval:draft` turns it into the two config files (`draft-check`, then `draft-apply` after the user approves). Every redraft starts from `RULES.md`, never from `EVAL_RULES.md`, which no longer holds the questions.

**There is no Electron.** The main process, the preload bridge, `electron-vite`, and `electron-builder` are all deleted, and the conversion that removed them is finished. The only host the UI has is the review server, the only build is the UI bundle, and the only way to install Qval is the plugin marketplace. Anything in the tree that still says "the app" means the same React UI, now served to a browser tab.

## Structure & process boundary

- `src/shared/`: `types.ts` and nothing else: the single source of truth for the data model + the **host contract** (`IpcApi`, still named for the IPC bridge it started as). Pure type declarations that compile to nothing. "Shared" is still the right word, though it no longer means what it did. It meant shared between the Electron main and renderer processes. It now means shared between the renderer, which imports these types, and `plugin/lib/`, whose JSDoc annotates against them. The pure *logic* used to live here too, and now lives once in `plugin/lib/`; the tests for it used to live here as well and are now in `test/lib/`.
- `src/renderer/`: React UI: `App.tsx` shell, `components/` (`ui/` primitives + feature components), `state/` (contexts via `createSafeContext`), `lib/` (utils, format, hooks). `lib/apiClient.ts` is the data layer: a `fetch` implementation of the same `IpcApi` interface, talking to the review server. It replaced the `contextBridge` preload, so the UI runs in an ordinary browser tab. `src/renderer/src/fonts.css` self-hosts Inter and IBM Plex Mono out of `@fontsource/*`, which the design has always named and nothing used to bundle.
- `plugin/ui/index.html`: the built UI: one self-contained file, every byte of JS, CSS, and font inlined by `vite-plugin-singlefile` (`vite.config.mts`). It is a **committed build artifact**, which is what keeps the plugin folder installable with no build step, so `npm run build` after any renderer change and commit the result. `npm run check:ui` rebuilds into a temp dir and fails on drift; CI runs it.
- `plugin/`: the **Claude Code plugin** we ship (`.claude-plugin/plugin.json`), listed by the repo-root `.claude-plugin/marketplace.json` so `/plugin marketplace add balevine/qval` then `/plugin install qval@qval` installs it. Skills live under `plugin/skills/` (`draft`, `evaluate-tickets`, `review`), the CLI under `plugin/bin/`. All three skills set `disable-model-invocation: true`, which is the one setting that keeps their descriptions out of the startup context entirely. The cost is that natural language no longer triggers them. Only `/qval:<name>` does.
- `plugin/skills/evaluate-tickets/`: the **Claude Code skill** that runs the LLM evaluation, which is the only way an LLM scores anything here: `SKILL.md` (what Claude follows) and `engine.mjs` (`init`/`config`/`draft-check`/`draft-apply`/`plan`/`assemble`/`retry`/`jev`/`status`). The skill verifies the config and runs it. It never writes one. The engine owns everything structural. Under `claude`, subagents only supply judgment. Under `jev`, there are no subagents and the engine does the whole run. `init` writes the starter config out of `DEFAULT_SCHEMA` and `DEFAULT_RULES` rather than copying template files. Those constants are the only definition of the starter config, because the review session's settings defaults (`settings.mjs`) and schema normalization fall back to the same two, and both copies would be hashed into the config fingerprint. A second copy that drifted would leave two users who each accepted the defaults unable to merge. Files it writes carry `provider: 'claude-code'` (Claude) or `provider: 'typesafe'` with `model: 'jev-latest'` (Jev).
- `plugin/server/server.mjs`: the localhost HTTP server behind `/qval:review`. Dependency-free node. Serves the single-file UI bundle plus the JSON endpoints over a `Workspace` the CLI has already bound to files. **No endpoint accepts a path**, which is what removes the path-traversal surface: a merge names a candidate id the CLI resolved, and an export names nothing at all. Access control is a token + `Host` allowlist + `Sec-Fetch-Site` stack, documented at the top of the file.
- `plugin/bin/qval`: the CLI, and the only thing that ever resolves a path: `serve` (resolve the files, start the server **detached**, open a browser, print the URL) and `status` (read back how the session ended, plus the eval file's counts). It lands on the Bash tool's PATH automatically while the plugin is enabled. The detachment is the point. Scoring 200 tickets by hand outlives any Bash timeout. It is extensionless on purpose: the shebang picks the interpreter and the filename *is* the command, so `qval.mjs serve` would be the alternative.
- `plugin/package.json`: three lines, `{"type": "module"}`, and **not deletable**. `bin/qval` is ESM with no extension, so without this marker node has to guess the module kind by reading the file, which it only does from 22.7 on. Node 20 (what the README promises) assumes CommonJS instead and dies on the first `import`. Verify with `NODE_OPTIONS=--no-experimental-detect-module npm test`, which reproduces an old node exactly.
- `plugin/skills/review/`: the **review skill** (`/qval:review`): a `SKILL.md` over that CLI. It runs no model and scores nothing.
- `plugin/skills/draft/`: the **draft skill** (`/qval:draft`), which runs first and is the only thing that writes `EVAL_SCHEMA.json` and `EVAL_RULES.md`. `SKILL.md` (scorer choice, drafting from `RULES.md` or a description, or the starter config via `init`) and `DRAFTING.md` (how Claude turns `RULES.md` into a draft, read only when drafting). It has no engine of its own. It calls `init`, `config`, `draft-check`, and `draft-apply` on the evaluation engine, so a draft is checked by the same code that checks a config before a run.
- `plugin/lib/`: **the** logic, and the only copy of it: `schema`, `rules`, `fingerprint`, `promptCompiler`, `evalValidate`, `evalFile`, `tickets`, `aggregate`, `settings`, `workspace`, `settingsStore`, `fsUtil`, `paths`, `args`, `host`, `version`, `draft`, `jev`, `typesafe`. `draft` reads and checks a drafted config (the envelope plus non-blocking warnings), which is the pure half of `draft-check`/`draft-apply`. `jev` compiles one Jev request per ticket and reads the response back into the raw values a subagent would have written, then hands them to `validateValues`, so a Jev answer is coerced or dropped by the same rules as a Claude one. `typesafe` is the one HTTP call Qval makes itself. It owns the key variable, the retries (408, 429, and 5xx only, at most two), and the redaction. `paths` holds the filenames Qval derives rather than asks for (`suggestEvalName`, `reportPathFor`); it sits apart from `workspace` because the engine needs them and has no business importing a `Workspace` to name a file. `args` owns both the parser and `flagValue`, which is what every subcommand in both entry points branches on. `host` holds the two ambient facts both entry points need from the machine, `nowIso` and `pidAlive`, which each of them used to define for itself. `evalFile.summarizeEvalFile` is there for the same reason: both `status` commands print a block about an eval file, and the two wordings had already drifted, so the same file described itself differently depending on which command you asked. Anything importing `node:*` here is host-only. The renderer imports `evalFile`, `schema`, `aggregate`, `evalValidate`, and `promptCompiler` through `@lib/*`, so those must stay free of node built-ins or the UI build breaks. **The version lives in `plugin/.claude-plugin/plugin.json` and nowhere else.** `version.mjs` reads it from there, so never reintroduce an `APP_VERSION` constant. A stale copy stamps a wrong `appVersion` into every eval file and nothing fails, which is why this is a rule and not a preference (Qbort has the same module for the same reason). `package.json` carries a second copy that npm requires; `version.test.ts` fails if the two drift. Dependency-free ESM, so it runs on bare `node` with no build step and no `npm install`. It sits above `skills/` because the engine, the review server, and the CLI all import it. The app imports the same files through the `@lib/*` alias. Exported signatures carry JSDoc `@param`/`@returns` pointing at `@shared/types`. That is what the TypeScript side type-checks against, and it is a comment to node, so both properties hold at once. **Keep the JSDoc accurate when you change a signature.** `checkJs` is off, so a wrong annotation degrades to `any` silently rather than erroring.

**Hard rule:** the renderer never touches Node, the filesystem, or a path. Everything crosses the boundary through the allow-listed surface declared in `shared/types.ts`, served by `plugin/server/server.mjs` over HTTP. **No endpoint accepts a path**: the CLI resolves every file before the browser exists, which is what removes the path-traversal surface rather than defending against it. That is why there is no OPEN, no Save-As, and no folder picker in the UI, and why merging picks a candidate by id. Anything the browser sends is re-validated host-side. The one secret, the Typesafe key, never reaches this boundary. Only the engine process reads it, and nothing the server or the browser handles carries it.

## Core domain model

- **Imported tickets**: `{ id, subject, status, messages: [{ from, body, isStaff, createdAt }] }`, wrapped in `{ meta, tickets }` or bare, read-only. Qval never mutates the dataset. Parsing is deliberately tolerant (only an integer `id` is fatal, unknown fields ignored) so a hand-written export is a first-class input. **Datasets are discovered by shape, never by filename**: every `.json` in the working directory is parsed and kept if it looks like tickets. `qbort-output/` is scanned too, because Qbort writes one timestamped run per file there, but it is a convenience for one known producer and nothing more. Several datasets in one place is ordinary. The eval file goes in **`qval-output/`** under the working directory regardless of where the dataset lives, which is where the engine writes its own and where merge candidates are scanned for. It never follows the dataset into a subdirectory, where neither half would find it.

**Two fixed directories, neither configurable** (`plugin/lib/paths.mjs` owns both names). `qval-output/` holds the durable artifacts (`*.qval.json`, `*.report.json`); `.qval-run/` holds scratch (compiled prompts, raw batch output, saved Jev responses, run context, a pending draft, the review session record, `settings.json`). **Both are gitignored.** They are generated files about a dataset, not source. Durable and committable are different questions: `qval-output/` is the one thing here that cannot be regenerated (a human evaluation is hours of work and has no other copy), which is why it is kept out of the scratch directory people delete, and why the docs must never suggest deleting it. There used to be an `--out` flag on both entry points: a review started under one value and an evaluation run under another could not see each other's state, which silently disabled the `SESSION_LIVE` guard, and nothing ever passed it. **Eval files written before `qval-output/` existed sit loose in the working directory, and both the open-resolution and the merge-candidate scan still look there** (`evalSearchDirs`, `defaultEvalPath`). Do not "tidy" that away: without it an upgrade starts a second empty evaluation beside a full one and the first symptom is a review that looks like it lost every score.
- **Scorer**: `claude` | `jev`, one per config and so one per eval file. `EVAL_SCHEMA.json` is `{ scorer, properties }`. A bare array (every file written before scorers existed) reads as `claude`, and anything Qval writes back is the wrapped form (`schemaFile`). The Jev fields on a property (`instructions`, `trueDescription`/`falseDescription`, `optionDescriptions`, `levels`, and on a multi-select the per-option `optionInstructions`/`optionTrueDescriptions`/`optionFalseDescriptions`) are kept by normalization only under `jev` and dropped under `claude`. A multi-select whose options have their own instructions (all or none, `OPTION_QUESTION_FIELDS`) sends each option as its own noul, built like qbench's grouped nouls, and hashes those fields only when present so older Jev configs keep their fingerprints. A Jev score's `min`/`max`/`step` come from its levels (`0..levels.length-1`, step 1). Jev cannot score `text` or a multi-valued `score`, and the question text (instructions plus description) must differ between properties. The two scorers never cross: `plan` refuses a `jev` config and `jev` refuses a `claude` one, both with `WRONG_SCORER`, so Claude subagents never score a Jev config and vice versa. The review UI shows the scorer read-only. Under `jev` its schema editor locks type, options, `multiple`, and the score range, and cannot add or remove a property, because those edits would leave `optionDescriptions` and `levels` describing answers that no longer exist.
- **Schema**: ordered `EvalProperty[]`; four base types: `score` (numeric min/max/step), `boolean`, `enum` (options), `text`. Each optionally **multi-valued** via `multiple: true` (array of that type; allowed for enum/score, not boolean/text, no nesting). `[]` on a multiple property = "none apply" (≠ missing key). Determines what can be aggregated.
- **Rules**: a single free-form text block (`string`) of evaluation context (prose, definitions, and/or a criteria list), decoupled from the schema; injected verbatim into the LLM prompt and shown next to the human form.
- **Eval file (`*.qval.json`)**: a list of **evaluators**, each with `kind` (`'llm'|'human'`), a display `name` (the human name comes from the run config), optional `provider`/`model` (llm), and an explicit `results[]` keyed by `ticketId` (sparse; partial `values` allowed). A typical working file has one `llm` + one `human` evaluator. Plus a snapshot of `{scorer, schema, rules}` and two fingerprints. One provider and one model score every ticket in a file (`PROVIDER_LOCKED`, `MODEL_LOCKED`). **The config lock begins at the first real score** (`configLocked`, any evaluator). Before it, a file whose config differs from the current `EVAL_*` pair adopts that pair rather than refusing. `plan` and `jev` restamp it and print `CONFIG_ADOPTED` after their first line, and `serve` restamps it on open. An unscored file records no decision anyone made, only what it was created with, so adopting loses nothing. After the first score, `plan` and `jev` refuse with `CONFIG_MISMATCH`, the review UI's schema and rules editors are disabled, and `draft-check`/`draft-apply` list the file under `OTHER_CRITERIA`. A Jev result also keeps the model Jev reported as `reportedModel`. It **references** the dataset by fingerprint (does not embed tickets).
- **Fingerprints**: `dataset.fingerprint` (SHA256 over canonicalized ticket content) and `config.fingerprint` (SHA256 over normalized schema + rules). **Merge requires both to be equal** (same tickets AND same schema AND same rules), else it's refused with a specific reason. **A `claude` config hashes exactly the payload it did before scorers existed**, with no scorer field in it, so every eval file already on disk keeps its fingerprint and still merges. `test/lib/fingerprint.test.ts` pins literal hashes for this, and a change that breaks them breaks every existing file silently. Only `jev` adds the scorer and the Jev fields to the hash, which is also what keeps a Jev file and a Claude file of the same rules from ever merging.
- **Aggregates**: derived at merge time, never persisted: score → mean/sd/n; boolean → counts/proportion + `majority` + `agreement`; enum → distribution + `mode` + `agreement`; multi-select (enum+multiple) → multi-hot per-option `distribution`/`selectionRate` + majority `consensus`; text (and score[] lists) → collected side-by-side (no mode). `agreement` = modal count ÷ n (the categorical analog of low variance); **ties → `mode`/`majority` = null** (distribution still shows the split). **LLM and human evaluators are pooled into two separate groups by `kind` and never combined into one number**. The headline output is the per-property **`comparison`** (LLM group vs human group: score Δ, majority match, or set jaccard), plus a dataset-level roll-up of how closely the model tracks human judgment. `comparison` is null where either side has no value. Evaluators are pooled across the working file + all comparison files; streams split by `kind` (llm vs human); missing values skipped. Side-by-side columns are evaluator `name`s; identity/dedup on `(kind, name, sourceFile)` with suffix disambiguation on name collisions.

## Evaluation pipeline

**One writer at a time.** The engine and the review server write the same `*.qval.json`, and the server holds its copy in memory for hours, so a stale write would erase a whole LLM run silently. Both directions are guarded. `plan`, `assemble`, and `jev` (at its start and again before its write) refuse with `SESSION_LIVE` (exit 2) when `.qval-run/review-session.json` says a session is live on that file with a pid still alive. `draft-apply` refuses when any session is live in the directory, because a session writes its own config back over the two files when it ends. `Workspace.adoptExternalWrite` re-reads the file before every server-side write, adopting a compatible newer copy and throwing on one whose dataset or config fingerprint has changed. Keep all of them. None covers another's window.

`loadRunEvalFile` in the engine is the mirror of `adoptExternalWrite` and compares the same two fingerprints. **A newer file is adopted, not refused** (`applyLlmResults` rebuilds only the `llm` evaluator, so a human evaluation made while the round was out survives), and only a changed dataset or changed config is `FILE_REPLACED`. The config half is load-bearing. `assemble` validates the batch files against the file's own schema, so adopting a copy whose criteria a review session had re-stamped would score the round against a schema its prompts never described. Do not put a timestamp comparison back here. It refuses the ordinary case, and the documented answer to a refusal is a re-`plan`, which calls `clearRunScratch` and throws away a whole round of subagent work that was never at risk.

**`.qval-run/` holds two kinds of file, and only one kind belongs to a single run.**

Files that belong to one evaluation run, and are deleted at the start of the next one: `prompt-<r>-<i>.txt` (the text given to a subagent), `batch-<r>-<i>.json` (what that subagent wrote back), `round-<r>.json` (which tickets went into which batch), and the `jev/` directory (one raw Jev response per ticket, `<ticketId>.json`). `run-context.json` (what the run is doing) belongs to one run too, but it is rewritten by every `plan` and `jev` rather than deleted.

Files that have to survive across runs: `settings.json` (the working scorer, schema, and rules, the evaluator's name, and where the tickets file was last found), `review-session.json` (whether a review session is open and how the last one ended. This is the only thing `qval status` has to report from, the only way the engine can tell a session is open, and the only place an error from the detached server is recorded), and `draft.json` (a drafted config waiting for the user's approval, which is not part of any run).

`plan` and `jev` call `clearRunScratch`, which deletes the first group by matching those exact filenames plus the `jev/` directory. It must never touch the second group, which is why it does not simply empty the directory the way Qbort does. Emptying it would lose the evaluator's name and make `qval status` answer "no session has run here" for a session that did. `jev --resume` is the one run that skips it, and it is only allowed onto the run that saved those responses (same eval file, dataset fingerprint, and config fingerprint in `run-context.json`, else `RESUME_MISMATCH`).

Deleting the first group is a correctness fix, not tidiness. Batch files are numbered, so a run with fewer batches reuses the filenames of a longer one. A leftover file whose subagent never wrote was read as the previous run's answers for the same ticket numbers, saved with a new timestamp and counted as a success, when `assemble` is supposed to record an error. Saved Jev responses carry the same hazard by ticket id. `clearRunScratch` runs only after `plan` or `jev` has finished checking its inputs, because a run that stops with an error has to leave the directory as it found it (including any responses a `--resume` would need).

**Claude runs** are batched, per-ticket output, and all of it lives in `plugin/skills/evaluate-tickets/engine.mjs`. `plan` picks the targets and splits them into batches, writing one compiled prompt file per batch (`compilePrompt`: rules + schema + rendered tickets + JSON output contract). Subagents read a prompt file and write a JSON object of schema-keyed values. `assemble` validates those, merges them into the eval file, and writes atomically. A batch that comes back short or unparseable is one `retry` round, not a transport-level retry. There is no socket to grow a token budget on.

**Jev runs** are one command, `jev`, which sends one request per ticket from Node (`toJev`, `postSystemOne`), writes each response to `.qval-run/jev/` before reading it, and folds the answers in through `readJev` and the same per-value validation. A multi-valued enum is asked as one yes-or-no question per option. A score answer between levels is snapped and recorded as `clamped`. There is no retry round. The transport retries 408, 429, and 5xx at most twice, a 401 or 403 stops sending (`KEY_REJECTED`), and an interrupted run continues with `--resume`. Tests stub `fetch`, and nothing in the suite touches the network.

**Validation is per-value, never per-ticket.** Each property is coerced when unambiguous (clamp score to range + snap step, coerce boolean, trim/case-match enum to a canonical option, stringify text) or **dropped** (left unscored) when not. One bad field never discards the ticket's other values. For a `multiple` property this means `[]` is reserved for a literal empty array. A null value, or a non-empty one whose every element is unusable, is **dropped** rather than reduced to "none apply". Answering `[]` on the model's behalf would invent a positive finding *and* count as scored, so the retry would never see it.

**Ticket text is untrusted.** Every ticket is rendered (for either scorer) fenced between `<<<TICKET n>>>` and `<<<END TICKET n>>>`, any such marker inside the subject, author name, or body is defused, and `SYSTEM_PROMPT` names that fence as the data/instruction boundary. Real helpdesk exports carry whatever a customer typed. Keep new prompt content outside the fences. Coercions/drops are recorded in the result's `issues[]` (non-silent). Under `claude`, any ticket with a drop or a ticket-level `error` gets **exactly one** automatic validation retry (capped to avoid loops). Residual failures stay as `issues`/`error`, for the human to answer in their own eval. **LLM values are never hand-edited.** To disagree with the model you fill in the human eval and the comparison shows the gap. Re-run modes: all / only-failed-or-unevaluated / a selection.

**The engine owns structure, and the scorer owns judgment.** Ticket `id` comes from the dataset and is never trusted from the model. The model returns only the schema-keyed values, re-validated against the schema before persistence. The engine reads the batch files and the Jev responses in node, so ticket content never enters the orchestrating agent's context.

**Drafting** (`/qval:draft`) follows the same split. Claude reads `plugin/skills/draft/DRAFTING.md` and `RULES.md` and writes `.qval-run/draft.json`. `draft-check` validates it with the same per-row checks `config` runs (so a draft that passes is a config that passes) and prints warnings, notes, what was removed from the rules, and the eval files that already hold scores under other criteria (`OTHER_CRITERIA`). `draft-apply` re-checks it and writes the two config files. Neither ever writes `RULES.md`.

## Code style

- TypeScript strict; `noUnusedLocals` is on, so no dead vars/imports. Path aliases `@shared/*` (types), `@lib/*` (the `.mjs` logic, imported with its extension), and `@/*` (renderer). One `tsconfig.json` covers everything, DOM and node libs together. The old node/web split was an electron-vite artifact and it forbade the test that drives the renderer's client against a real `node:http` server.
- **camelCase** everywhere (data model + code). Property `key`s are camelCase and stable.
- Every module in `plugin/lib/` ships a `*.test.ts` named after it in `test/lib/` (**Vitest**). That is a rule, not a description: adding a module there means adding its test file, and the list is currently complete. They sit apart from the code they cover rather than beside it because a `.test.ts` inside the shippable plugin folder would need vitest and TypeScript to run, and `plugin/` has to stay dependency-free and installable with no build step. The renderer's own tests have no such constraint and are co-located (`src/renderer/src/lib/*.test.ts`). Tests are deterministic: no real network, and `now` is injectable. Keep it that way. Fingerprint and aggregate reducers are pure and exhaustively tested.
- `test/lib/` holds the unit tests for `plugin/lib/`, one file per module. `test/` itself holds the suites that cross the repo/plugin boundary, which is the distinction between the two: everything directly under `test/` spawns a process or binds a port, and everything in `test/lib/` is pure. `skillEngine.test.ts` drives the engine's subcommands over `child_process` in a temp dir, with pre-written batch files standing in for subagents, `cli.test.ts` drives `bin/qval` the same way (killing the detached child it leaves behind), `server.test.ts` drives the review server over real HTTP on an OS-assigned loopback port, and `reviewRoundTrip.test.ts` drives the renderer's own `apiClient` against that server and merges the result with a file the engine wrote.
- Prefer pure, testable helpers; keep side effects (fs, http) at the edges. Writes go through `fsUtil.atomicWriteJson`.
- Comments explain **why**, not what; match the surrounding density.
- When writing comments and markdown files, prefer periods and parenthesis over semi-colons, colons, and em-dashes. When in doubt, end the sentence and start a new one. Two plain sentences beat one joined by punctuation.

## Visual design

Neo-brutalist, strictly **monochrome** black/white/grays, minimal, high-contrast. Tokens in `tailwind.config.cjs`: `ink` (black), `paper` (white); the only permitted non-monochrome surface is `staff` (slate) for staff messages in the conversation view. Hard **2px black borders**, **square corners** (`rounded-none`), solid offset shadows (`shadow-brutal`), flat fills (no gradients), **UPPERCASE mono** buttons/labels. shadcn/Radix primitives are restyled to this language in `components/ui/`. Status/aggregates are conveyed by borders/weight/labels, not color.

## Commands

`npm run typecheck` · `npm test` · `npm run build` (writes `plugin/ui/index.html`) · `npm run check:ui` (is the committed bundle current?) · `npm run dev` (vite dev server for the UI, which has no API of its own. Start a review server and point at it with `QVAL_DEV_SERVER=http://127.0.0.1:PORT`, then open the vite URL with that server's `?t=` token). Run `typecheck` + `test` before considering a change done, and `build` too if you touched the renderer.

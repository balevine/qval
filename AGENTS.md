# AGENTS.md

Guidance for agentic coding tools working in this repo: where things live, the invariants to preserve, and the conventions to write to. It describes **how to work here**, not what the product is.

**[`README.md`](README.md) is the authoritative definition of the application** — what Qval does, the ticket format, what each command is for, how the pieces fit. Read it first, and **keep it in sync whenever behavior changes**; a change that makes the README wrong is not finished. Where this file and the README overlap, the README is the one that has to be right, and the orientation below is a summary of it for working purposes.

`.plans/` is a historical artifact: gitignored, unmaintained, and **not to be updated**. Nothing in the code or the docs cites it any more, and nothing should start: a comment that needs to justify a decision should state the reason itself rather than point at a document the reader may not have.

## What this is

A local-first tool for **evaluating** customer support tickets, shipped as a **Claude Code plugin**. It scores any ticket set in the documented format — a real helpdesk export as readily as a set generated by **Qbort**, its sibling tool. Qbort is one producer of the format, not a dependency, and docs must not imply otherwise. The user imports a ticket set, writes free-text **rules** (how to score), defines a typed **schema** of output properties, runs an **LLM evaluation**, optionally does a **human evaluation** by hand, and saves both into a single `*.qval.json` file. Multiple users' eval files of the same dataset can be **merged** for per-ticket **means/standard deviations** (LLMs and humans disagree even on the same model/criteria).

**Claude does the LLM work, and nothing else does.** The evaluation runs inside Claude Code with the ambient model (`/qval:evaluate-tickets`). There is no provider picker, no API key, and no in-app run. The whole provider stack (Ollama, bring-your-own-key, `safeStorage`, the cost estimate) was deleted, not deprecated. The parts a person has to do by hand (schema, rules, human eval, comparison) open in a browser tab served by the review server (`/qval:review`). Everything runs locally; the only network egress is Claude Code's own.

Both halves read and write the same `EVAL_SCHEMA.json` and `EVAL_RULES.md` in the working directory. `qval serve` seeds a new session from them and writes back what the person actually used, which is what stops the two commands from scoring against different criteria and producing files that will not merge. The write-back is **conditional**: the config fingerprint is taken at session start and again at the end, and the files are only rewritten when it changed. They are the user's files, often hand-written, and a session opened on an older eval file loads *that* file's config — so an unconditional write would stamp an archived schema over the current one just for looking at an old result.

**There is no Electron.** The main process, the preload bridge, `electron-vite`, and `electron-builder` are all deleted, and the conversion that removed them is finished. The only host the UI has is the review server, the only build is the UI bundle, and the only way to install Qval is the plugin marketplace. Anything in the tree that still says "the app" means the same React UI, now served to a browser tab.

## Structure & process boundary

- `src/shared/` — `types.ts`, the single source of truth for the data model + the **host contract** (`IpcApi`, still named for the IPC bridge it started as). Pure type declarations that compile to nothing. The pure *logic* used to live here too; it now lives once, in `plugin/lib/`. The `*.test.ts` files still here cover those `lib/` modules, since a `.test.ts` inside the shippable plugin folder would need vitest and TypeScript to run.
- `src/renderer/` — React UI: `App.tsx` shell, `components/` (`ui/` primitives + feature components), `state/` (contexts via `createSafeContext`), `lib/` (utils, format, hooks). `lib/apiClient.ts` is the data layer: a `fetch` implementation of the same `IpcApi` interface, talking to the review server. It replaced the `contextBridge` preload, so the UI runs in an ordinary browser tab. `src/renderer/src/fonts.css` self-hosts Inter and IBM Plex Mono out of `@fontsource/*`, which the design has always named and nothing used to bundle.
- `plugin/ui/index.html` — the built UI: one self-contained file, every byte of JS, CSS, and font inlined by `vite-plugin-singlefile` (`vite.config.mts`). It is a **committed build artifact**, which is what keeps the plugin folder installable with no build step, so `npm run build` after any renderer change and commit the result. `npm run check:ui` rebuilds into a temp dir and fails on drift; CI runs it.
- `plugin/` — the **Claude Code plugin** we ship (`.claude-plugin/plugin.json`), listed by the repo-root `.claude-plugin/marketplace.json` so `/plugin marketplace add balevine/qval` then `/plugin install qval@qval` installs it. Skills live under `plugin/skills/` (`evaluate-tickets`, `review`), the CLI under `plugin/bin/`. Both skills set `disable-model-invocation: true`, which is the one setting that keeps their descriptions out of the startup context entirely — the cost being that natural language no longer triggers them, only `/qval:<name>` does.
- `plugin/skills/evaluate-tickets/` — the **Claude Code skill** that runs the LLM evaluation with the ambient model (no API key), which is now the only way an LLM scores anything here: `SKILL.md` (what Claude follows), `engine.mjs` (`init`/`config`/`plan`/`assemble`/`retry`/`status`), `templates/`. The engine owns everything structural; subagents only supply judgment. Files it writes carry `provider: 'claude-code'`.
- `plugin/server/server.mjs` — the localhost HTTP server behind `/qval:review`. Dependency-free node. Serves the single-file UI bundle plus the JSON endpoints over a `Workspace` the CLI has already bound to files. **No endpoint accepts a path**, which is what removes the path-traversal surface: a merge names a candidate id the CLI resolved, and an export names nothing at all. Access control is a token + `Host` allowlist + `Sec-Fetch-Site` stack, documented at the top of the file.
- `plugin/bin/qval` — the CLI, and the only thing that ever resolves a path: `serve` (resolve the files, start the server **detached**, open a browser, print the URL) and `status` (read back how the session ended, plus the eval file's counts). It lands on the Bash tool's PATH automatically while the plugin is enabled. The detachment is the point — scoring 200 tickets by hand outlives any Bash timeout. It is extensionless on purpose: the shebang picks the interpreter and the filename *is* the command, so `qval.mjs serve` would be the alternative.
- `plugin/package.json` — three lines, `{"type": "module"}`, and **not deletable**. `bin/qval` is ESM with no extension, so without this marker node has to guess the module kind by reading the file, which it only does from 22.7 on. Node 20 (what the README promises) assumes CommonJS instead and dies on the first `import`. Verify with `NODE_OPTIONS=--no-experimental-detect-module npm test`, which reproduces an old node exactly.
- `plugin/skills/review/` — the **review skill** (`/qval:review`): a `SKILL.md` over that CLI. It runs no model and scores nothing.
- `plugin/lib/` — **the** logic, and the only copy of it: `schema`, `rules`, `fingerprint`, `promptCompiler`, `evalValidate`, `evalFile`, `tickets`, `aggregate`, `settings`, `workspace`, `settingsStore`, `fsUtil`, `paths`, `args`, `version`. `paths` holds the filenames Qval derives rather than asks for (`suggestEvalName`, `reportPathFor`); it sits apart from `workspace` because the engine needs them and has no business importing a `Workspace` to name a file. `args` owns both the parser and `flagValue`, which is what every subcommand in both entry points branches on. Anything importing `node:*` here is host-only — the renderer imports `evalFile`, `schema`, `aggregate`, and `promptCompiler` through `@lib/*`, so those four must stay free of node built-ins or the UI build breaks. **The version lives in `plugin/.claude-plugin/plugin.json` and nowhere else** — `version.mjs` reads it from there, so never reintroduce an `APP_VERSION` constant. A stale copy stamps a wrong `appVersion` into every eval file and nothing fails, which is why this is a rule and not a preference (Qbort has the same module for the same reason). `package.json` carries a second copy that npm requires; `version.test.ts` fails if the two drift. Dependency-free ESM, so it runs on bare `node` with no build step and no `npm install`. It sits above `skills/` because the engine, the review server, and the CLI all import it. The app imports the same files through the `@lib/*` alias. Exported signatures carry JSDoc `@param`/`@returns` pointing at `@shared/types`. That is what the TypeScript side type-checks against, and it is a comment to node, so both properties hold at once. **Keep the JSDoc accurate when you change a signature** — `checkJs` is off, so a wrong annotation degrades to `any` silently rather than erroring.

**Hard rule:** the renderer never touches Node, the filesystem, or a path. Everything crosses the boundary through the allow-listed surface declared in `shared/types.ts`, served by `plugin/server/server.mjs` over HTTP. **No endpoint accepts a path**: the CLI resolves every file before the browser exists, which is what removes the path-traversal surface rather than defending against it. That is why there is no OPEN, no Save-As, and no folder picker in the UI, and why merging picks a candidate by id. Anything the browser sends is re-validated host-side. There are no secrets on either side of the boundary any more — the evaluation runs on the ambient model, so there is no key to hold.

## Core domain model

- **Imported tickets** — `{ id, subject, status, messages: [{ from, body, isStaff, createdAt }] }`, wrapped in `{ meta, tickets }` or bare, read-only. Qval never mutates the dataset. Parsing is deliberately tolerant (only an integer `id` is fatal, unknown fields ignored) so a hand-written export is a first-class input. **Datasets are discovered by shape, never by filename**: every `.json` in the working directory is parsed and kept if it looks like tickets. `qbort-output/` is scanned too, because Qbort writes one timestamped run per file there, but it is a convenience for one known producer and nothing more. Several datasets in one place is ordinary. The eval file goes in **`qval-output/`** under the working directory regardless of where the dataset lives, which is where the engine writes its own and where merge candidates are scanned for. It never follows the dataset into a subdirectory, where neither half would find it.

**Two fixed directories, neither configurable** (`plugin/lib/paths.mjs` owns both names). `qval-output/` holds the durable artifacts (`*.qval.json`, `*.report.json`); `.qval-run/` holds scratch (compiled prompts, raw batch output, run context, the review session record, `settings.json`). **Both are gitignored** — they are generated files about a dataset, not source. Durable and committable are different questions: `qval-output/` is the one thing here that cannot be regenerated (a human evaluation is hours of work and has no other copy), which is why it is kept out of the scratch directory people delete, and why the docs must never suggest deleting it. There used to be an `--out` flag on both entry points: a review started under one value and an evaluation run under another could not see each other's state, which silently disabled the `SESSION_LIVE` guard, and nothing ever passed it. **Eval files written before `qval-output/` existed sit loose in the working directory, and both the open-resolution and the merge-candidate scan still look there** (`evalSearchDirs`, `defaultEvalPath`). Do not "tidy" that away: without it an upgrade starts a second empty evaluation beside a full one and the first symptom is a review that looks like it lost every score.
- **Schema** — ordered `EvalProperty[]`; four base types: `score` (numeric min/max/step), `boolean`, `enum` (options), `text`. Each optionally **multi-valued** via `multiple: true` (array of that type; allowed for enum/score, not boolean/text, no nesting). `[]` on a multiple property = "none apply" (≠ missing key). Determines what can be aggregated.
- **Rules** — a single free-form text block (`string`) of evaluation context (prose, definitions, and/or a criteria list), decoupled from the schema; injected verbatim into the LLM prompt and shown next to the human form.
- **Eval file (`*.qval.json`)** — a list of **evaluators**, each with `kind` (`'llm'|'human'`), a display `name` (the human name comes from the run config), optional `provider`/`model` (llm), and an explicit `results[]` keyed by `ticketId` (sparse; partial `values` allowed). A typical working file has one `llm` + one `human` evaluator. Plus a snapshot of `{schema, rules}` and two fingerprints. It **references** the dataset by fingerprint (does not embed tickets).
- **Fingerprints** — `dataset.fingerprint` (SHA256 over canonicalized ticket content) and `config.fingerprint` (SHA256 over normalized schema + rules). **Merge requires both to be equal** — same tickets AND same schema AND same rules — else it's refused with a specific reason.
- **Aggregates** — derived at merge time, never persisted: score → mean/sd/n; boolean → counts/proportion + `majority` + `agreement`; enum → distribution + `mode` + `agreement`; multi-select (enum+multiple) → multi-hot per-option `distribution`/`selectionRate` + majority `consensus`; text (and score[] lists) → collected side-by-side (no mode). `agreement` = modal count ÷ n (the categorical analog of low variance); **ties → `mode`/`majority` = null** (distribution still shows the split). **LLM and human evaluators are pooled into two separate groups by `kind` and never combined into one number** — the headline output is the per-property **`comparison`** (LLM group vs human group: score Δ, majority match, or set jaccard), plus a dataset-level roll-up of how closely the model tracks human judgment. `comparison` is null where either side has no value. Evaluators are pooled across the working file + all comparison files; streams split by `kind` (llm vs human); missing values skipped. Side-by-side columns are evaluator `name`s; identity/dedup on `(kind, name, sourceFile)` with suffix disambiguation on name collisions.

## Evaluation pipeline

**One writer at a time.** The engine and the review server write the same `*.qval.json`, and the server holds its copy in memory for hours, so a stale write would erase a whole LLM run silently. Both directions are guarded: `plan` and `assemble` refuse (`SESSION_LIVE`, exit 2) when `.qval-run/review-session.json` says a session is live on that file with a pid still alive, and `Workspace.adoptExternalWrite` re-reads the file before every server-side write, adopting a compatible newer copy and throwing on one whose dataset or config fingerprint has changed. Keep both. Neither covers the other's window.

**`.qval-run/` holds two kinds of file, and only one kind belongs to a single run.**

Files that belong to one evaluation run, and are deleted at the start of the next one: `prompt-<r>-<i>.txt` (the text given to a subagent), `batch-<r>-<i>.json` (what that subagent wrote back), `round-<r>.json` (which tickets went into which batch), and `run-context.json` (what the run is doing).

Files that have to survive across runs: `settings.json` (the working schema and rules, the evaluator's name, and where the tickets file was last found), and `review-session.json` (whether a review session is open and how the last one ended — this is the only thing `qval status` has to report from, the only way the engine can tell a session is open, and the only place an error from the detached server is recorded).

`plan` calls `clearRunScratch`, which deletes the first group by matching those exact filenames. It must never touch the second group, which is why it does not simply empty the directory the way Qbort does. Emptying it would lose the evaluator's name and make `qval status` answer "no session has run here" for a session that did.

Deleting the first group is a correctness fix, not tidiness. Batch files are numbered, so a run with fewer batches reuses the filenames of a longer one. A leftover file whose subagent never wrote was read as the previous run's answers for the same ticket numbers, saved with a new timestamp and counted as a success, when `assemble` is supposed to record an error. `clearRunScratch` runs only after `plan` has finished checking its inputs, because a `plan` that stops with an error has to leave the directory as it found it.

Batched, per-ticket output, and it all lives in `plugin/skills/evaluate-tickets/engine.mjs` now. `plan` picks the targets and splits them into batches, writing one compiled prompt file per batch (`compilePrompt`: rules + schema + rendered tickets + JSON output contract). Subagents read a prompt file and write a JSON object of schema-keyed values. `assemble` validates those, merges them into the eval file, and writes atomically. A batch that comes back short or unparseable is one `retry` round, not a transport-level retry — there is no socket to grow a token budget on.

**Validation is per-value, never per-ticket:** each property is coerced when unambiguous (clamp score to range + snap step; coerce boolean; trim/case-match enum to a canonical option; stringify text) or **dropped** (left unscored) when not — one bad field never discards the ticket's other values. For a `multiple` property this means `[]` is reserved for a literal empty array: a null value, or a non-empty one whose every element is unusable, is **dropped** rather than reduced to "none apply". Answering `[]` on the model's behalf would invent a positive finding *and* count as scored, so the retry would never see it.

**Ticket text is untrusted.** Every ticket is rendered into the prompt fenced between `<<<TICKET n>>>` and `<<<END TICKET n>>>`, any such marker inside the subject, author name, or body is defused, and `SYSTEM_PROMPT` names that fence as the data/instruction boundary. Real helpdesk exports carry whatever a customer typed. Keep new prompt content outside the fences. Coercions/drops are recorded in the result's `issues[]` (non-silent). Any ticket with a drop or a ticket-level `error` gets **exactly one** automatic validation retry (capped to avoid loops); residual failures stay as `issues`/`error`, for the human to answer in their own eval. **LLM values are never hand-edited** — to disagree with the model you fill in the human eval and the comparison shows the gap. Re-run modes: all / only-failed-or-unevaluated / a selection.

**The engine owns structure; the LLM owns judgment.** Ticket `id` comes from the dataset and is never trusted from the model; the model returns only the schema-keyed values, re-validated against the schema before persistence. The engine reads the batch files in node, so ticket content never enters the orchestrating agent's context.

## Code style

- TypeScript strict; `noUnusedLocals` is on — no dead vars/imports. Path aliases `@shared/*` (types), `@lib/*` (the `.mjs` logic, imported with its extension), and `@/*` (renderer). One `tsconfig.json` covers everything, DOM and node libs together. The old node/web split was an electron-vite artifact and it forbade the test that drives the renderer's client against a real `node:http` server.
- **camelCase** everywhere (data model + code). Property `key`s are camelCase and stable.
- Every module in `plugin/lib/` ships a `*.test.ts` named after it in `src/shared/` (**Vitest**). That is a rule, not a description: adding a module there means adding its test file, and the list is currently complete. Tests are deterministic: no real network, and `now` is injectable — keep it that way. Fingerprint and aggregate reducers are pure and exhaustively tested.
- `test/` holds the suites that cross the repo/plugin boundary: `skillEngine.test.ts` drives the engine's subcommands over `child_process` in a temp dir, with pre-written batch files standing in for subagents, `cli.test.ts` drives `bin/qval` the same way (killing the detached child it leaves behind), `server.test.ts` drives the review server over real HTTP on an OS-assigned loopback port, and `reviewRoundTrip.test.ts` drives the renderer's own `apiClient` against that server and merges the result with a file the engine wrote.
- Prefer pure, testable helpers; keep side effects (fs, http) at the edges. Writes go through `fsUtil.atomicWriteJson`.
- Comments explain **why**, not what; match the surrounding density.
- When writing comments and markdown files, prefer periods and parenthesis over semi-colons, colons, and em-dashes. When in doubt, end the sentence and start a new one. Two plain sentences beat one joined by punctuation.

## Visual design

Neo-brutalist, strictly **monochrome** black/white/grays, minimal, high-contrast. Tokens in `tailwind.config.cjs`: `ink` (black), `paper` (white); the only permitted non-monochrome surface is `staff` (slate) for staff messages in the conversation view. Hard **2px black borders**, **square corners** (`rounded-none`), solid offset shadows (`shadow-brutal`), flat fills (no gradients), **UPPERCASE mono** buttons/labels. shadcn/Radix primitives are restyled to this language in `components/ui/`. Status/aggregates are conveyed by borders/weight/labels, not color.

## Commands

`npm run typecheck` · `npm test` · `npm run build` (writes `plugin/ui/index.html`) · `npm run check:ui` (is the committed bundle current?) · `npm run dev` (vite dev server for the UI, which has no API of its own — start a review server and point at it with `QVAL_DEV_SERVER=http://127.0.0.1:PORT`, then open the vite URL with that server's `?t=` token). Run `typecheck` + `test` before considering a change done, and `build` too if you touched the renderer.

## Notes

- **There is no packaging any more.** `electron-builder.yml`, the release workflow, and the DMG are gone. Distribution is the plugin marketplace, and the whole shipped artifact is the `plugin/` folder. The last unsigned DMG stays on GitHub Releases for anyone with old files, which still open and still merge (they just carry an older `provider` string).
- There is **no cost accounting**. Ambient generation isn't a metered API call, so there is nothing to estimate and no pre-run gate.
- **Markdown is soft-wrapped**: one line per paragraph or bullet, no hard wrap at a fixed column (it reads badly at narrow widths). Applies to every `.md` in the repo, including `README.md` (user-facing), `.plans/`, and the skills' `SKILL.md`/`README.md`. `.notes/` is gitignored scratch.
- Contribution rule: open an Issue before a PR.
